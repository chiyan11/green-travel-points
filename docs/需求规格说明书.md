| 问题 | 结论 |
|---|---|
| 系统是什么 | 把"绿色出行行为"变成**可计量、可核查、可兑换**的碳资产的 Web 平台 |
| 谁在用 | 市民（C 端）、运营管理员、商户、碳核证/风控、模拟数据源、定时任务（共 6 个角色） |

## 1. 项目概述与迭代规划

### 1.1 项目背景与目标

**问题**：城市交通碳排放占城市总排放的比重持续上升，而市民的步行、骑行、公共交通出行缺乏可量化的记录与正向激励。现有碳普惠平台普遍存在三个痛点：出行数据不可信（无从校验）、积分规则不透明（用户算不出自己的分）、多方结算难（商户供了货，积分怎么核销、怎么结账说不清）。

**系统目标**：构建一个鼓励市民采用绿色出行方式的积分激励平台，实现四件事——
1. **出行数据采集（模拟）**：接收并校验市民上报的行程（方式、距离、时间）；
2. **碳减排量计算**：相对"燃油私家车基准"计算少排放的 CO₂ 当量；
3. **积分累积与兑换**：按公开规则换算积分、记账、在积分商城兑换商品；
4. **商城运营管理**：商品/库存/订单/商户/对账的运营闭环。

**目标用户与价值**：

| 利益相关方 | 核心诉求 | 系统提供的价值 |
|---|---|---|
| 市民 | 出行有回报、规则看得懂、兑换不踩坑 | 行程即积分，明细可查，兑换有凭证 |
| 运营管理员 | 规则可配置、异常可干预、数据可对账 | 参数化运营，不靠发版改规则 |
| 商户 | 订单可履约、结算有依据 | 订单通知 + 核销码 + 商户对账单 |
| 碳核证/风控 | 减排量口径合规、刷分可拦截 | 行程可审计、幂等防重、账户可冻结 |
| 指导教师/答辩 | 架构有取舍、模型与代码一致 | 全套 UML + EDA 落地证据 |

**成功标准（可验收）**：

| 编号 | 成功标准 | 验收方式 |
|---|---|---|
| G1 | 5 种出行方式的碳减排与积分结果**唯一且可复现** | `apps/api/internal/domain/` 单测全绿，与需求文档数值表逐行对照 |
| G2 | 账本等价恒等式任何时刻成立 | `make reconcile` 对账命令输出"偏差 0" |
| G3 | 50 并发兑换同一 SKU，**超卖 = 0** | 并发集成测试报告（实验四） |
| G4 | "上报→得积分→兑换→核销"端到端可演示 | E2E 用例 + 演示脚本 |
| G5 | 核心图表与代码/数据库命名一致 | 设计说明书自查表（用例名 ↔ 接口 ↔ 表名） |

### 1.2 迭代规划

采用敏捷开发，1–2 周一个 Sprint，每个 Sprint 末提交**可工作的软件增量**（指导书硬性要求）。

| Sprint | 周期 | 核心目标 | 可工作增量（Demo） | 对齐实验 |
|---|---|---|---|---|
| S0 | 第 1 周 | 选题确认、技术栈验证、业务规则冻结、骨架搭建 | 空壳前后端 + MySQL 连通 + CI 跑通 | 准备 |
| S1 | 第 2–4 周 | **需求建模**：角色/用例/活动图/域模型/非功能需求 + 架构选型 | 本文件定稿 + 用户故事地图 + 全套分析模型 | 实验一 |

## 2. 系统用例分析

### 2.1 角色分析

**表 1-1　角色列表**

| 编号 | 角色名 | 所属部门 | 简要描述 |
|---|---|---|---|
| R1 | 市民（出行用户） | 公众 / 城市居民 | 通过 Web 端上报步行、骑行、公交、地铁、共享单车行程；查询碳减排量与积分；浏览并兑换积分商城商品；查看订单与核销码；对异常记录申诉。 |
| R2 | 运营管理员 | 平台运营部 | 维护商品与 SKU、上下架、调库存；处理兑换订单（审核/发货/核销）；配置排放因子与积分参数；对异常账户冻结/调账；查看运营看板与对账报表。 |
| R3 | 商户（合作商家） | 外部合作机构 | 提供积分商城商品货源；接收新订单通知、确认发货、提交核销结果；查看本商户的兑换明细与结算单。 |
| R4 | 碳核证 / 风控专员 | 平台碳资产部 | 复核异常行程（距离越界、频次异常、瞬时速度不合理）；冻结可疑账户；处理事件死信与重放；确认碳减排量核算口径符合公示口径。 |
| R5 | 交通数据提供方（模拟） | 外部系统 | 以 HTTP 接口 / 定时任务推送或校验出行数据，是"出行数据采集"的触发者。本项目由模拟器实现，用于产生可复现的测试数据集。 |
| R6 | 定时任务（时间触发者） | 平台后台 | 触发每日积分清算、积分过期、报表生成、Outbox 事件重试与死信扫描；无人工操作界面，但作为系统参与者建模。 |

#### 2.3.2 关键用例的事件流

**UC-02 上报出行行程**

| 项 | 内容 |
|---|---|
| 参与者 | R1 市民 |
| 前置条件 | 已登录；账户未被冻结 |
| 触发 | 用户在"申报"页提交表单或调用 `POST /api/v1/trips` |
| 基本流 | 1. 系统校验必填项与格式（方式、距离、起止时间）<br>2. 校验距离 ∈ [0.1, 100] km<br>3. 计算 `trip_hash`，查幂等表：已存在则直接返回首次结果（不重复发放）<br>4. 查 `travel_mode` 取排放因子<br>5. 计算 `carbon_saved = distance × (EF_base − EF_actual)`，下界 0<br>6. `points = floor(carbon_saved / carbon_per_point)`，套当日上限<br>7. 单事务写：`trip_record` + `carbon_record` + `point_txn` + 更新 `point_account` + 写 `event_outbox(TripVerified)`<br>8. 返回本次减排量与获得积分 |
| 备选流 | 2a. 距离越界 → 400 `E_DISTANCE_OUT_OF_RANGE`，提示允许区间<br>3a. 幂等命中 → 200 返回首次结果，标记 `deduplicated=true`<br>5a. 因子倒挂（EF_actual > EF_base）→ 减排量取 0，仍记录行程但不发分<br>6a. 当日已达上限 → 本次发放削减为剩余额度，标记 `capped_by_daily=true`<br>7a. 账户已冻结 → 403 `E_ACCOUNT_FROZEN`，不写任何数据 |
| 后置条件 | 行程与流水可查；`PointsGranted` 事件进入 Outbox 等待异步消费 |
| 业务规则 | BR-01, BR-02, BR-03, BR-04, BR-05, BR-06, BR-07 |

**UC-08 兑换商品**

| 项 | 内容 |
|---|---|
| 参与者 | R1 市民 |
| 前置条件 | 已登录；`balance − frozen ≥ 商品所需积分`；SKU 有库存且已上架 |
| 触发 | `POST /api/v1/redeem-orders`（必须带 `Idempotency-Key`） |
| 基本流 | 1. 校验幂等键：已处理过则返回原订单<br>2. 开启事务<br>3. `SELECT ... FOR UPDATE` 锁积分账户行与 SKU 库存行<br>4. 复核积分充足性与库存 > 0（**锁后复核，禁止先查后写**）<br>5. 扣减积分：插 `point_txn(type=REDEEM, amount<0)` + 更新 `point_account.balance`<br>6. 扣减库存：`product_sku.stock = stock − 1`<br>7. 创建 `redeem_order(status=PENDING)`，生成核销码<br>8. 写 `event_outbox(OrderPaid)`，提交事务<br>9. 返回订单号与核销码 |
| 备选流 | 1a. 幂等键重复 → 200 返回首次订单，**不重复扣分**<br>4a. 积分不足 → 409 `E_INSUFFICIENT_POINTS`，事务回滚<br>4b. 库存不足 → 409 `E_OUT_OF_STOCK`，事务回滚<br>4c. 商品已下架 → 409 `E_PRODUCT_OFFLINE`<br>8a. 事务提交后 Worker 失败 → 事件留在 Outbox 由重试消费（积分不回滚，符合"扣分即成立"） |
| 后置条件 | 积分减少且流水与余额一致；库存减一；订单进入 `PENDING` |
| 业务规则 | BR-09, BR-10, BR-11, BR-13, BR-15 |

### 2.4 数据建模（名词短语法 + CRC）

#### 2.4.1 名词短语提取（名词短语法）

从选题描述与 §1–§2 的需求文字中抽取名词/名词短语，逐个判定归属：

| 名词短语 | 判定 | 说明 |
|---|---|---|
| 市民、运营管理员、商户 | **角色 → Actor** | 不进类图（除非需要人员档案，见下） |
| 用户账户 | **实体类 `User`** | 含账户状态、积分账户的归属方 |
| 出行记录 | **实体类 `TripRecord`** | 一次行程的事实 |
| 碳减排量 | **实体类 `CarbonRecord`** | 与行程 1:1，独立成记录便于重算与追溯 |
| 碳积分 | **实体类 `PointAccount` + `PointTxn`** | 拆成"余额快照"与"流水账本"两个类（关键设计决策） |
| 商品 | **实体类 `Product`** | 商品主数据 |
| 商品规格/库存 | **实体类 `ProductSku`** | 可兑换的最小单位，库存挂在 SKU 上 |
| 积分商城 | **不建类** | 是 Product 的视图/页面，不是实体 |
| 订单 / 兑换记录 | **实体类 `RedeemOrder`** | 有生命周期与状态机 |
| 商户 | **实体类 `Merchant`** | 商品归属与结算主体 |
| 出行方式（公交/地铁/骑行） | **实体类 `TravelMode`（字典表）** | 方式 → 排放因子的载体 |
| 积分规则/排放因子 | **实体类 `SysConfig`** | 参数化，禁止硬编码 |
| 出行数据采集 | **控制类 `TripIntakeService`** | 动词派生 |
| 积分发放/清算 | **控制类 `PointsService` / `ReconcileJob`** | 动词派生 |
| 距离、时间、余额、单价 | **属性** | 不独立成类 |
| 碳中和、绿色出行 | **不建类** | 领域背景描述词 |

**两条判定口径（写进报告，答辩可复述）**：
1. **动词派生控制类**：需求里的动词（采集、计算、核发、兑换、清算）→ 控制类；**名词派生实体类**：需要持久化且有生命周期的名词 → 实体类。
2. **"积分"必须一分为二**：`PointAccount` 是**余额快照**（可被并发更新），`PointTxn` 是**只增不改的流水**（事实来源）。二者分离才能同时满足"查得快"和"可对账"（BR-07/BR-08）。

#### 2.4.2 CRC 卡片（核心 6 个类）

| 类 | 职责（Responsibilities） | 协作者（Collaborators） |
|---|---|---|
| `TripRecord` 出行记录 | 保存方式、距离、起止时间、`trip_hash`；保证同一用户同一行程只存一次 | `User`、`TravelMode`、`CarbonRecord` |
| `CarbonRecord` 碳减排记录 | 记录 EF_base、EF_actual、减排克数、计算时的规则版本；支持重算与追溯 | `TripRecord`、`SysConfig` |
| `PointAccount` 积分账户 | 持有 `balance` / `frozen` / `expired`；校验"可用积分 ≥ 需求"；提供原子扣减 | `PointTxn`、`RedeemOrder` |
| `PointTxn` 积分流水 | **只插入**；记录变动类型、数量、关联业务 ID、发生时间；是余额的唯一事实来源 | `PointAccount`、`TripRecord`、`RedeemOrder` |
| `Product` + `ProductSku` 商品与规格 | 商品主数据、所需积分、上下架状态；SKU 持有库存并保证"不超兑" | `Merchant`、`RedeemOrder` |
| `RedeemOrder` 兑换订单 | 持有订单号、积分快照、核销码；维护状态机并拒绝非法跃迁 | `PointAccount`、`ProductSku`、`EventOutbox` |

#### 2.4.3 域模型

见 `docs/uml/04-域模型.puml`。实体清单与关系基数（答辩时逐条讲）：

| 实体 | 关键关系 | 基数 |
|---|---|---|
| `User` 1 — * `TripRecord` | 一个用户多条行程 | 1 : 0..* |
| `TripRecord` 1 — 1 `CarbonRecord` | 一次行程一条碳记录 | 1 : 1 |
| `User` 1 — 1 `PointAccount` | 一人一账户 | 1 : 1 |
| `PointAccount` 1 — * `PointTxn` | 一账户多条流水 | 1 : 0..* |
| `Merchant` 1 — * `Product` | 商户供多款商品 | 1 : 0..* |
| `Product` 1 — * `ProductSku` | 一款商品多个规格 | 1 : 0..* |
| `User` 1 — * `RedeemOrder` * — 1 `ProductSku` | 兑换的多对多，用订单承载 | * : * 经 `RedeemOrder` |
| `RedeemOrder` 1 — * `PointTxn` | 一次兑换可能触发多条流水（扣减/冲正） | 1 : 0..* |
| `TravelMode` * — 1 `EmissionFactor`（合并于 `TravelMode` 表） | 方式携带因子 | — |
| `EventOutbox` * — 1 业务对象 | 事件关联业务 ID | 多态引用 |

### 2.5 业务规则（编号化，测试直接引用）

| 编号 | 规则 | 可验证形式 |
|---|---|---|
| BR-01 | `carbon_saved = max(0, distance × (EF_base − EF_actual))`，单位 gCO₂e | 5 种方式数值表单测 |
| BR-02 | 排放因子与 `carbon_per_point`、日上限、距离区间、有效期**全部来自 `sys_config` / `travel_mode` 表**，代码不得硬编码 | 代码评审 + 改库值不改代码即生效 |
| BR-03 | `points = floor(carbon_saved / carbon_per_point)`，加 1e-9 容差吸收浮点误差；向下取整保证不透支 | 边界：99.999→0、100→1、300→3、453→4 |
| BR-04 | 单日积分上限默认 500，超出部分削平并标记 `capped_by_daily` | 当日已发 480，再得 50 → 实发 20 |
| BR-05 | 单次行程距离 ∈ [0.1, 100] km；NaN/Inf/≤0 一律拒绝 | 0.09 拒、0.1 过、100 过、100.1 拒 |
| BR-06 | **上报幂等**：`user_id + trip_hash` 唯一；重复上报只产生 1 条行程、1 笔流水 | 并发重复提交测试 |
| BR-07 | **账本等价**：`point_account.balance == Σ(point_txn.amount)`，任何时刻成立 | 对账任务偏差 = 0 |
| BR-08 | 流水表 **append-only**：不 update、不 delete；冲正用反向流水表达 | 代码中无 UPDATE point_txn |
| BR-09 | **不超兑**：`balance − frozen ≥ 所需积分`，且库存 > 0；必须 `SELECT ... FOR UPDATE` 锁后复核 | 50 并发超卖 = 0 |
| BR-10 | 订单状态机 `PENDING → PAID → SHIPPED → COMPLETED`，可 `CANCELLED`；非法跃迁必须拒绝并留痕 | 状态机单测覆盖全部非法边 |
| BR-11 | 积分有效期 365 天，扣减按**先进先出**（最早到期先扣） | 过期用例 |
| BR-12 | 订单取消/超时：积分与库存**原路回滚**（补反向流水，不改原流水） | 取消后余额复位 |
| BR-13 | 事件**至少一次**投递，消费端必须幂等（按 `event_id` 去重） | 重复投递不重复发分 |
| BR-14 | 人工调账与配置变更**必须**写 `audit_log`（操作人/前后值/理由）；配置与调账分权 | 审计表可查 |
| BR-15 | 兑换请求 `Idempotency-Key` 在 24h 内重复 → 返回原订单，不重复扣分 | 幂等键重放测试 |

**事件目录（EDA 的建模依据，写进设计说明书 2.1.1）**

| 事件 | 发布时机 | 消费方与动作 |
|---|---|---|
| `TripVerified` | 行程落库并核发积分后 | 更新碳减排统计、成就徽章、排行榜 |
| `PointsGranted` | 积分流水写入后 | 推送通知、日上限累计更新 |
| `OrderPaid` | 兑换订单创建后 | 库存二次校验、通知商户、生成核销码、写报表 |
| `OrderShipped` | 运营发货后 | 通知用户、更新履约时效统计 |
| `OrderCompleted` | 核销完成 | 商户结算累计、用户积分消耗统计 |
| `PointsExpired` | 每日清算发现过期 | 写过期流水、推送提醒 |
| `AccountFrozen` | 风控冻结 | 中断后续发分、标记在途订单 |

> 一致性策略：业务写与事件写**同一本地事务**（Outbox），Worker 轮询投递 → 天然满足"业务成功则事件必达"；消费端按 `event_id` 幂等 → 满足"至少一次投递不重复生效"。

## 3. 非功能需求

> 原则：每条 NFR **必须带数值指标或显式的"本版不验证"**，否则无法写进测试报告（实验四）。

| 编号 | 类别 | 指标（可测） | 验证方式 |
|---|---|---|---|
| NFR-01 | 性能 | 行程上报 P95 ≤ 200 ms；积分查询 P95 ≤ 150 ms；兑换下单 P95 ≤ 300 ms（单机 4C8G，MySQL 同机） | k6 / `go test -bench` |
| NFR-02 | 并发一致性 | 同一 SKU 50 并发兑换：超卖 = 0，账本偏差 = 0 | 并发集成测试 |
| NFR-03 | 数据一致性 | 账本等价恒等式成立率 100%；T+1 对账偏差 = 0 | `make reconcile` |
| NFR-04 | 可用性 | 演示环境不承诺 SLA；核心接口错误率 < 1%（压测口径） | 压测报告 |
| NFR-05 | 安全 | 密码 bcrypt cost ≥ 10；JWT 2h 过期；越权返回 403；单用户限流 20 rps；参数配置与积分调账**分权**（不同角色） | 安全用例 + 代码评审 |
| NFR-06 | 可观测性 | 日志含 `trace_id` 与请求 ID；提供 `/healthz`、`/readyz`；Outbox 积压与消费延迟可查 | 接口冒烟 + 日志抽样 |
| NFR-07 | 可维护性 | 核心域单测覆盖率 ≥ 90%，全仓 ≥ 70%；`gofmt -l` 与 `go vet` 零告警；CI 红灯不得合并 | CI 报告 |
| NFR-08 | 兼容性 | Chrome / Edge 最近两个大版本；最小分辨率 1280×720 | 手工走查 |
| NFR-09 | 隐私与合规 | 个人信息最小化：只存手机号 + 昵称 + 密码摘要；**不采集精确 GPS 轨迹**，只存起终点名称与距离；日志脱敏手机号 | 数据表评审 |
| NFR-10 | 可移植性 | `docker compose up -d` 一条命令拉起 mysql + api + web；部署到云主机可公网访问 | 部署演练 |
| NFR-11 | 可扩展性 | 新增一种出行方式只需加 `travel_mode` 一行数据 + 无代码改动；新增事件类型只需加消费端订阅 | 演示：加"步行-电动轮椅"方式 |
| NFR-12 | 审计 | 所有积分变动可反查来源（行程/兑换/调账/过期）；`audit_log` 保留 ≥ 180 天 | 追溯用例 |
