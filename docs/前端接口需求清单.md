# 前端接口需求清单（P4 → P2/P3）

> 用途：Sprint 1–2 联调前，把用户端 8 个页面需要的端点、字段、分页与错误码一次性提给后端。
> 口径来源：`docs/项目分工与迭代计划.md`、`apps/api/internal/domain`、`db/migrations/000001`；机器可读契约见 `docs/api/openapi.yaml`。
> 约定：所有响应走统一壳 `{code, message, data}`；字段命名（camelCase / snake_case）以 `docs/api/openapi.yaml` 为准（人读说明见 `docs/api/README.md`）。
> 前端现状：`apps/web/src/services/*` 已按真实接口实现（无 MOCK 分支）；wire 类型由 `docs/api/openapi.yaml` 生成到 `apps/web/src/types/api.ts`（`npm run gen:api`），页面视图模型仍是手写的 `apps/web/src/types/domain.ts`，两者在 service 层做映射。

## 0. 全局约定

| 项 | 约定 |
| --- | --- |
| 鉴权 | 登录后请求头 `Authorization: Bearer <token>`；401 前端清会话跳 `/login` |
| 分页 | 查询参数 `page`（从 1 起）、`pageSize`（默认 20）；响应 `{ items, page, pageSize, total }` |
| 时间 | 统一 ISO 8601（带时区），前端 `formatDateTime` 本地格式化 |
| 积分 | 整数 BIGINT，禁止浮点；碳排放 `DECIMAL(12,3)` 克 |
| 错误码 | 复用 `internal/httpserver/response.go`：OK / INVALID_ARGUMENT / UNAUTHORIZED / FORBIDDEN / NOT_FOUND / CONFLICT / INTERNAL / UNAVAILABLE；业务细分 `INSUFFICIENT_POINTS` / `OUT_OF_STOCK` / `LIMIT_EXCEEDED` / `ILLEGAL_TRANSITION`，均走 HTTP 409 |
| 幂等 | 上报行程带 `Idempotency-Key` 头；重复兑换请求同键只扣一次 |

## M1 用户与认证（P2）

### POST /api/v1/auth/register
请求：
```json
{ "phone": "13800000001", "password": "至少6位", "nickname": "宋同学" }
```
`phone` 必填（`account` 同义，二选一）；`nickname` 可选，缺省取手机号。
响应 data：`{ "userId": "u_xxx", "nickname": "宋同学", "token": "<自签 HMAC 紧凑串>" }`
错误：`CONFLICT`（手机号已注册）、`INVALID_ARGUMENT`（密码不足 6 位 / 手机号为空）。

### POST /api/v1/auth/login
请求：`{ "phone": "13800000001", "password": "..." }`（`account` 同义，二选一）
响应 data：`{ "token": "<自签 HMAC 紧凑串>", "user": { "userId", "nickname" } }`（不是标准 JWT）
错误：`UNAUTHORIZED`（账号或密码错误）。

### GET /api/v1/me
响应 data：`{ "userId", "nickname", "joinedAt" }`；401 时前端跳登录。

## M2 行程上报与碳核算（P2，复用 domain.EvaluateTrip）

### GET /api/v1/trips
查询：`page`、`pageSize`、`status=VALID|REVOKED`（对齐 trip_record.status，000004）、`from`、`to`（ISO 日期）。
响应 `items[]`：
```json
{
  "id": "trip_xxx",
  "mode": "subway",
  "distanceKm": 3.2,
  "traveledAt": "2026-10-18T08:10:00+09:00",
  "carbonSavedGrams": 483.2,
  "rawPoints": 4,
  "grantedPoints": 4,
  "cappedByDaily": false,
  "status": "VALID"
}
```

> wire 字段是 `traveledAt`（对齐 `trip_record.traveled_at`），前端 service 层映射为视图模型的 `startedAt`，页面不要直接用 wire 名。

### POST /api/v1/trips
请求：
```json
{ "mode": "subway", "distanceKm": 3.2, "traveledAt": "2026-10-18T08:10:00+09:00" }
```
- `mode` 枚举：`walk | bike | subway | bus | shared_bike`
- `distanceKm`：0.1–100（含端点），非法返回 `INVALID_ARGUMENT`
- 响应 data 同上单条 Trip；必须返回 `rawPoints` 与 `grantedPoints` 两个值，前端要展示"原始/实发"和封顶原因
- 幂等：同 `userId + trip_hash` 重复上报只产生 1 条记录、1 笔流水，重复提交返回首次结果（HTTP 200）

## M3/M5 积分账户与流水（P2+P3）

### GET /api/v1/points/summary
```json
{
  "balance": 1280,
  "frozen": 0,
  "available": 1280,
  "totalCarbonSavedGrams": 2435.2,
  "earnedThisMonth": 22,
  "earnedToday": 4,
  "dailyCap": 500
}
```
不变量：`balance == Σ(point_txn.amount)`；`available = balance - frozen`，兑换校验用 `available`。对账口径见 `GET /api/v1/admin/points/reconcile`。

### GET /api/v1/points/daily-carbon
查询：`days`（默认 7，上限 90）。
响应 data：`[{ "date": "2026-11-24", "grams": 483.2 }, ...]`（按天聚合的碳减排克数，正序）。
前端 `services/points.ts` 的 `getCarbonSeries` 已对接。

### GET /api/v1/points/transactions
查询：`page`、`pageSize`、`type=TRAVEL|REDEEM|REFUND|ADJUST|EXPIRE`（对齐 point_txn.txn_type，000003）。
`items[]`：`{ id, type, amount(正得负耗), balanceAfter, reason, refType: "trip_record|redeem_order", refId, createdAt }`（wire 名以 `docs/api/openapi.yaml` 为准；前端 `toPointTxn` 映射为视图模型的 `bizRefType` / `bizRefId` / `occurredAt`）。
说明：`point_txn` 表无 reason 列，`reason` 由后端按 `type` 派生中文文案返回，不接受自由文本；`refType` 目前只有 `trip_record` / `redeem_order`。

## M6 商品与库存（P3）

### GET /api/v1/products
查询：`page`、`pageSize`、`category`、`keyword`、`onlyInStock=true`。
`items[]`：`{ id, name, description, category, coverUrl, status: "DRAFT|ONLINE|OFFLINE", pointsPrice, stock, limitPerUser }`。
（对齐 product/product_sku，000005；coverUrl=cover_url，列表只返回 ONLINE。）

### GET /api/v1/products/{id}
单条商品；下架/不存在返回 `NOT_FOUND`。

## M7 兑换下单与订单状态机（P3）

### POST /api/v1/orders
请求：`{ "productId": "p_1", "receiver": "本人" }`
- 预校验失败：积分不足 `CONFLICT`（或自定义 INSUFFICIENT_POINTS）、库存不足 `CONFLICT`、超限兑 `INVALID_ARGUMENT`
- 成功响应：`{ id, orderNo, productId, skuId, skuName, productName, pointsSpent, quantity, status: "PENDING", receiver, redeemCode, createdAt, updatedAt }`
（对齐 redeem_order，000005；redeemCode 在 SHIPPED 后生成。）
- 扣减/冻结走事务 + 行锁，禁止先查后写；并发不超卖

### GET /api/v1/orders
查询：`page`、`pageSize`、`status=PENDING|PAID|SHIPPED|COMPLETED|CANCELLED`。

### POST /api/v1/orders/{id}/cancel
仅 `PENDING` 可取消；返还积分、恢复库存、写冲正流水；非法跃迁返回 `CONFLICT`。

### 订单状态机（前端按钮按此禁用）
```
PENDING ──→ PAID ──→ SHIPPED ──→ COMPLETED
   │          │
   └──→ CANCELLED ←──┘
```

## 2026-11-17 认证/行程联调发现的差异（请后端确认）

接 P2 的 auth/trips 接口时发现两处不一致，前端已做兼容，但建议后端对齐后删掉兼容层：

| 位置 | 后端现状（`httpserver/trips.go`、迁移 000004） | 前端契约 | 处理方式 |
| --- | --- | --- | --- |
| 行程时间字段 | JSON 用 `traveledAt` | `startedAt`（= `trip_record.started_at`） | 前端 service 层 `toTrip` 固定读 `traveledAt` 并映射为 `startedAt`；上报按 `traveledAt` 发送，无兼容分支（`apps/web/src/services/trips.ts:27-38,51`） |
| 行程状态 | POST 响应硬编码 `"VERIFIED"`，列表返回库里的 `VALID/REVOKED` | `VALID \| REVOKED` | 前端把 `VERIFIED` 归一成 `VALID`，否则页面会出现第三种状态值 |
| 行程列表分页 | `GET /trips` 不分页，一次返回全部 | 期望 `{items,page,pageSize,total}` | 后端已按该结构返回（page=1、total=条数），前端按 `items` 消费，数据量大时需补分页 |
| 注册入参 | 需要 `phone`（或 `account`），`nickname` 可省略，密码 ≥6 位 | 同 | 前端注册表单按手机号 + 密码 + 可选昵称实现 |
