## 1 概述

### 1.1 目的与范围

本文件回答三个问题：

1. 为什么在“5 人、13 周、教学演示、单 MySQL”的约束下，选择**分层单体 + 事务性 Outbox**，而不是纯同步三层、微服务或事件溯源；
2. 系统由哪些包、类、表组成，它们之间的依赖方向是什么；
3. 关键用例（行程上报、兑换下单）的事务边界、锁顺序、幂等与失败回滚如何落地。

范围覆盖实验二要求的设计规格五部分：体系结构设计（含至少两种方案对比）、用例实现（鲁棒图 / 序列图 / 表 2-1）、关键程序逻辑（活动图）、数据库表清单（表 2-2）与字段级清单（表 2-3）。不包含实验三的界面截图与实验四的测试报告，那两部分分别在 `docs/实验报告-绿行积分.md` 第三、四章引用。

### 1.2 设计输入与约束

| 编号 | 约束 | 来源 / 事实 | 对设计的影响 |
|---|---|---|---|
| C1 | 5 人团队、13 周、每周可交付增量 | `docs/项目分工与迭代计划.md` §1、§4 | 不引入需要专职运维的中间件；优先单库、单进程 |

### 1.3 术语

| 术语 | 含义 |
|---|---|
| Outbox | `event_outbox` 表：业务事务内写事件，后台 Worker 轮询投递，保证“业务成功 ⇒ 事件不丢” |
| 事务性发件箱 | 同上；本项目的 EDA 最小实现，不依赖 MQ |
| 分层单体 | 一个进程、一个数据库，但代码按 `httpserver → app → domain`、`repo → app` 分层 |
| 端口 / 适配器 | `internal/app/ports.go` 定义存储能力，`internal/repo` 提供 MySQL 实现 |
| 批次 FIFO | `point_batch` 按 `expires_at ASC, id ASC` 扣减，支持 365 天过期 |
| 设计类 | 鲁棒图中的 Entity / Control / Boundary 三类职责，不是数据库表的同义词 |

### 1.4 与实现的总体对齐声明

截至 2026-11-24，仓库真实状态是：

- 后端目录为 `apps/api/internal/{app,config,domain,eventbus,httpserver,repo}`，**没有** `internal/usecase`；
- `sqlc.yaml` 存在但未启用，repo 为手写 SQL；
- Token 为自签 HMAC-SHA256 紧凑串，**不是标准 JWT**；密码为加盐 SHA-256（临时方案）；
- `eventbus` 已有轮询 Worker，支持重试与死信；默认处理器仅记录投递，业务消费者待各模块接入；
- `deploy/docker-compose.yml` 只有 `mysql` + `api`，web/nginx 未编入；
- 数据库共 7 组迁移、15 张表（含 `point_batch_txn` 与 `audit_log`），不是早期文档写的 13 张。

这些差异不影响“分层单体 + Outbox”的选型结论，但影响图与文档的可信度。§2 的图按**当前实现**画，§4 集中列出偏差与处理计划。

## 2 系统设计

### 2.1 体系结构设计

#### 2.1.1 架构决策与选型

指导书要求“至少分析两种以上软件架构方案，分析不同方案对约束条件的支持程度并选择”。本节先比较三种方案，再给出决策与理由。

**（1）候选架构方案与约束支持度**

**表 2-0　候选架构方案对比**

| 方案 | 组成 | 一致性 | 事件解耦 | 运维成本 | 对 13 周 / 5 人的适配 | 结论 |
|---|---|---|---|---|---|---|
| A. 经典三层同步单体 | Controller → Service → Repository，单 MySQL；积分发放、通知、统计全部同步调用 | 强（本地事务） | 弱：通知/统计与主链路耦合，失败会拖慢或回滚主链路 | 低 | 高：最容易在 2 周内跑通 | 作为基线，不选 |
| B. 分层单体 + 事务性 Outbox | 同一进程内分层；业务事务内写 `event_outbox`，消费者异步轮询 | 核心账务强一致；事件最终一致 | 强：业务与通知/统计解耦，事件可重试、可重放 | 中低：只需一张表 + 一个 Worker | 高：先跑通主链路，再补 Worker | **选用** |
| C. 微服务 + Kafka/RabbitMQ | 用户、行程、积分、商城、通知拆服务；MQ 做事件总线 | 最终一致；跨服务需 Saga / 补偿 | 最强 | 高：需要 MQ、服务发现、链路追踪、分布式事务 | 低：5 人 13 周无法稳定交付 | 不选 |

**表 2-0A　约束支持度矩阵**（强 / 中 / 弱）

| 约束 | A 同步三层 | B 单体 + Outbox | C 微服务 + MQ |
|---|---|---|---|
| C1 5 人 13 周 | 强 | 强 | 弱 |
| C2 1–2 周迭代 | 强 | 强 | 弱 |
| C3 单 MySQL、无 MQ | 强 | 强 | 弱（需新增中间件） |
| C4 积分/库存强一致 | 强 | 强（本地事务） | 中（Saga 补偿复杂） |
| C5 事件不丢、可重试 | 弱 | 强（Outbox） | 强（MQ 持久化） |
| C6 Windows 开发、低运维 | 强 | 强 | 弱 |
| C7 既定 Go/React 技术栈 | 强 | 强 | 中（多语言/多仓库） |
| C8 可单测、可演示 | 强 | 强（domain 纯函数） | 中（联调成本高） |

结论：A 能满足 C4，但 C5 弱；C 能满足 C5，但 C1/C2/C3/C6 明显不满足；B 在“核心账务强一致 + 事件最终一致”之间取得平衡，是唯一同时满足 C1–C8 的方案。

**（2）架构决策与选型理由**

**表 2-1A　架构决策记录（ADR 摘要）**

| 编号 | 决策 | 备选 | 理由 | 被否方案的问题 |
|---|---|---|---|---|
| D-01 | 采用**分层单体**，不拆微服务 | 微服务 + MQ | 单库本地事务即可保证积分/库存/订单原子；5 人团队不需要独立部署单元 | 分布式事务、服务发现、链路追踪会吃掉大部分工期 |
| D-02 | 采用**事务性 Outbox**，不用同步调用做通知/统计 | 同步调用；直接发 MQ | 业务写与事件写在同一个 `tx`，提交即“事件必达”；不引入 MQ | 同步调用失败会回滚主链路或丢通知；直接发 MQ 有“写库成功、发消息失败”的双写问题 |
| D-03 | 存储用**单 MySQL + 逻辑外键** | 分库分表；物理外键 | 数据量教学级；逻辑外键便于迁移与测试造数 | 分库分表超出课程范围；物理外键在批量迁移时难处理 |
| D-04 | 端口接口放 `internal/app`，repo 实现 | handler 直接依赖 `*sql.DB` | 可用假存储做 HTTP 单测，不连 MySQL | 直接依赖 DB 会让单测必须起库，CI 变慢 |
| D-05 | 认证目标为 JWT + bcrypt；当前实现为自签 HMAC + 加盐 SHA-256 | 继续用临时方案；换 OAuth | 课程要求能讲清认证与角色；临时方案不能写成“已实现 JWT” | 把 HMAC 写成 JWT 属于文档失真；OAuth 超出范围 |
| D-06 | 前端类型目标为 OpenAPI 生成；当前为手写 `types/domain.ts` | 继续手写；引入 tRPC | 生成可减少字段漂移；当前先保证页面可用 | 手写会随接口变化漂移；tRPC 会改技术栈 |
| D-07 | 部署目标为 compose 拉起 mysql + api + web + nginx；当前只拉起 mysql + api | 继续本地双进程；上云 | 一条命令演示是 NFR-10 的门槛 | 当前未满足 NFR-10，不能写成“已部署” |

**为什么是“分层单体 + Outbox”，而不是别的？**

1. **一致性边界**：积分余额、库存、订单、流水必须在同一事务内完成。单库本地事务是最便宜、最容易讲清楚的强一致方案；拆成微服务后，同样的需求要引入 Saga、幂等补偿、对账，13 周内很难稳定。
2. **事件解耦**：选题 14 明确建议“用 EDA 处理出行后积分发放与清算解耦”。Outbox 让“行程上报”只负责写事件，通知/统计/清算可以后置；消费者失败不回滚已发放积分，符合“扣分即成立”的业务语义。
3. **失败可恢复**：`event_outbox` 的 `attempts / available_at / dispatched_at / dead_letter_at / last_error` 支持退避重试与死信；这是同步调用没有的。
4. **可测试性**：domain 是纯函数，HTTP 层注入端口，repo 才碰 SQL；因此 45 个领域用例、24 个 HTTP 用例不需要 MySQL。
5. **成本**：不需要 Kafka、Redis、服务发现；一张表 + 一个轮询 goroutine 即可，和 5 人/13 周匹配。

**代价与边界**：

- 事件是“至少一次”，消费端必须幂等；Worker 已实现并启动，但当前处理器只记录日志，业务消费端（通知/统计/清算）尚未接入，幂等语义尚未真正支付。
- Outbox 表会膨胀，需要归档/清理策略；教学项目暂不处理。
- 前端类型已由 `docs/api/openapi.yaml` 生成到 `apps/web/src/types/api.ts`（`npm run gen:api`），字段漂移风险由门禁第 5 步兜住（§4 D-06）。

**包职责与依赖方向**

| 包 | 职责 | 允许依赖 | 禁止依赖 |
|---|---|---|---|
| `apps/web/pages` | 页面与路由级组合 | `services`、`components`、`types` | 直接 `fetch`、直接读 localStorage |
| `apps/web/services` | 按域封装的 API 调用，吸收后端字段差异 | `lib/http`、`types/domain` | 页面组件、DOM |
| `apps/web/lib/http.ts` | Envelope 解包、错误映射、401 清理会话并跳登录 | `lib/session` | 具体页面 |
| `apps/web/types/domain.ts` | 前端共享类型；当前手写，目标由 OpenAPI 生成 | 无 | 运行时逻辑 |
| `apps/api/cmd/server` | 装配 config → repo → 端口实现 → httpserver | 所有 internal 包 | 业务规则实现 |
| `apps/api/internal/httpserver` | 路由、中间件、handler、统一响应壳 | `app`、`domain` | 行程通过 `app.TripStore` 调用 repo；认证仍是直写 SQL 的例外（见 §4） |
| `apps/api/internal/app` | DTO、Ports 接口、哨兵错误 | 标准库 | `repo`、`httpserver` |
| `apps/api/internal/domain` | 碳核算、积分规则、订单状态机；纯函数 | 标准库 | `net/http`、`database/sql`、第三方包 |
| `apps/api/internal/repo` | 手写 SQL、事务、行锁、Outbox 写入 | `app`、`domain`、`database/sql` | `net/http` |
| `apps/api/internal/eventbus` | 事件 Topic / Event / Handler 契约 | 标准库 | 具体 repo / 消费者 |
| `apps/api/internal/config` | 环境变量 → Config，无 `.env` 解析 | 标准库 | 业务包 |

**依赖规则**：

```
web: pages → services → lib/http → fetch
api: cmd → httpserver → app
              httpserver → domain
              repo → app（实现 Ports）
              repo → domain
              repo → eventbus（写 Outbox）
              repo → MySQL
domain: 只依赖标准库
```

**与旧版图的差异**（旧图曾画 `internal/usecase`、`repo sqlc`、`lib/types.ts 由 openapi 生成`）：

- 删除 `internal/usecase`：当前没有这一层，handler 直接调端口；这是实现偏差，不是设计目标。目标态可以补 usecase，但不在本轮文档里假装已有。
- 删除 `sqlc`：`apps/api/sqlc.yaml` 只是配置，repo 全是手写 SQL。
- 删除“OpenAPI 生成”：`apps/web/src/types/domain.ts` 明确写着“手写契约版”。
- 保留“Worker 投递”：`eventbus.Worker` 已实现轮询、指数退避与死信（`apps/api/internal/eventbus/eventbus.go`），并在 `cmd/server/main.go` 启动；设计图按现状画。仍缺手动重放/死信查询接口。

#### 2.2.2 关键程序逻辑设计

**兑换下单与批次扣减**（图2-14）是并发与一致性最关键的逻辑，活动图按 `OrderHandler → Store → MySQL` 的真实调用顺序画：

![图2-14 活动图：兑换下单与积分批次扣减](docs/uml/out/图2-14%20活动图：兑换下单与积分批次扣减.png)

关键点：

1. **幂等先于事务**：`findOrderByIdem` 在 `BEGIN` 之前查；命中直接返回原订单，不重复扣分。并发下同一幂等键由 `uk_order_idem` 兜底，冲突后回读原订单。
2. **锁顺序固定**：先 `point_account` 行锁，再 `product_sku` 行锁；所有下单路径同一顺序，避免死锁。
3. **锁后复核**：商品 `ONLINE`、`stock > 0`、`balance − frozen ≥ price`、`limit_per_user` 未超限，全部在拿到行锁后判断，禁止“先查后写”。
4. **同一事务**：`redeem_order` + `point_txn(REDEEM)` + `point_account.balance` + `product_sku.stock` + `point_batch` 扣减 + `event_outbox(OrderPaid)` 同一 `tx`，任一步失败整体回滚。
5. **批次 FIFO**：`ORDER BY expires_at ASC, id ASC FOR UPDATE`，逐批扣 `remaining`；扣到 0 置 `CONSUMED`，每笔消耗写 `point_batch_txn`（amount 为负）。行程发放在 `repo/trips.go` 的行程事务内调用 `GrantPointsWithBatch` 写入 `point_batch`；批次不足时 `consumeBatches` 返回 `app.ErrInsufficientPoints` 并整体回滚（PR #40）；**剩余偏差**是 `consumeBatches` 未过滤已过期批次，过期批次仍可能被优先扣减（§4 D-03）。
6. **取消原路回滚**：只允许 `PENDING`；补 `REFUND` 流水，先按 `point_batch_txn` 把已消耗批次原路回填（`expires_at` 不变，amount 为正），未覆盖部分才新建退款批次；再退余额、回补库存、置 `CANCELLED`、写 `OrderCancelled` 事件；不修改原 `REDEEM` 流水。

**订单状态机**（图2-16）与**积分批次状态机**（图2-17）：

![图2-16 状态图：兑换订单生命周期](docs/uml/out/图2-16%20状态图：兑换订单生命周期.png)

![图2-17 状态图：积分批次生命周期](docs/uml/out/图2-17%20状态图：积分批次生命周期.png)

- 订单：`PENDING → PAID | CANCELLED`；`PAID → SHIPPED | CANCELLED`；`SHIPPED → COMPLETED | CANCELLED`。非法跃迁返回 `ILLEGAL_TRANSITION`。
- 批次：`ACTIVE → CONSUMED | EXPIRED | REVERSED`；取消时优先把消耗过的原批次回填为 `ACTIVE`（`expires_at` 不变），找不到消费明细的历史数据才新建退款批次。

## 5 结论

- **选型结论**：在 5 人/13 周/单 MySQL/无 MQ 的约束下，分层单体 + 事务性 Outbox 是同时满足“核心账务强一致、事件最终一致、低运维、可单测”的方案；微服务与纯同步三层分别在成本与解耦上不满足约束。
- **设计落地**：15 张表、7 组迁移、端口/适配器分层、行锁与唯一索引兜底已落地；订单与积分主链路可运行。
- **必须补的洞**：D-02（JWT/bcrypt）、D-03（过期批次过滤与自动过期）、D-04（业务消费者与死信重放）、D-05（compose 全栈）。D-01 已由行程事务迁入 repo 关闭。这些不补，“设计规格”只能算“主链路设计”，不能算“完整实现”。
- **文档边界**：本文件不把目标态写成现状；§4 的每一条都能对应到代码行或文件，答辩时按表回答“为什么还没做、什么时候做、谁负责”。
