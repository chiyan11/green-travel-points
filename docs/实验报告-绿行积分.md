# 摘要

本报告面向《软件工程实验》2026 版第 14 题“碳中和城市绿色出行积分系统”，给出从需求分析、系统设计到原型实现、测试与部署的阶段性成果。系统把步行、骑行、地铁、公交、共享单车五类出行换算为相对燃油小汽车的碳减排量，再按“100 克减排 = 1 积分”入账，支持积分查询、商城浏览、兑换下单与运营履约。

本版报告的重点是实验一与实验二：需求侧给出角色、19 个基本用例、分析类模型、业务规则和非功能指标；设计侧给出三种架构方案的约束对比，选择“分层单体 + 事务性 Outbox”，并给出包图、部署图、覆盖 19 个用例的鲁棒图/序列图（新增 27 张，全量 51 张 UML）、设计类清单、15 张表的表名清单与字段级清单。实验三、四按仓库当前状态给出已实现部分、可复现证据和明确的待补清单，不把计划写成已完成。

**关键词**：绿色出行；碳减排；积分账本；事务性发件箱；UML；分层单体

# 第一章 需求规格说明书

## 1.1 背景与目标

城市交通是碳排放的重要来源，小汽车每公里约排放 192 克 CO₂。步行、骑行、地铁、公交、共享单车相对燃油小汽车有不同程度的减排。项目把这些减排量转成可计量、可查询、可兑换的积分，形成“绿色出行—碳减排—积分—兑换”的闭环。

系统服务三类人工角色（市民、运营管理员、商户）和三类系统参与者（碳核证/风控、交通数据提供方、定时任务）。本期目标不是做真实碳交易，而是把“算得清、记得住、兑得掉、对得上”四件事做成可演示、可测试的教学系统。

**表 0-1　成功标准（可验收）**

| 编号 | 成功标准 | 验收方式 |
|---|---|---|
| G1 | 5 种出行方式的碳减排与积分结果唯一且可复现 | `internal/domain` 表驱动单测，与规则表逐行对照 |
| G2 | 账本等价恒等式任何时刻成立 | `GET /api/v1/admin/points/reconcile` 输出“偏差 0” |
| G3 | 50 并发兑换同一 SKU，超卖 = 0 | 已建 repo 集成用例 `TestCreateOrderConcurrentNoOversell`（20 并发，库存 5 → 成功 5、库存 0），CI 的 `mysql:8.4` service 上实际执行 |
| G4 | “上报→得积分→兑换→核销”端到端可演示 | `e2e/main-flow.spec.ts` 2 例已建（注册→上报→积分→兑换→取消、登录失败）；运营后台用例按本机种子条件运行 |
| G5 | 核心图表与代码/数据库命名一致 | 设计说明书 §4 偏差表 + 自查记录 |

**范围边界**：不做真实 GPS/轨迹、不做真实支付、不做真实物流、不做原生 App、不做多城市因子区划、不引入 Kafka/RabbitMQ；用“起终点 + 距离”模拟行程，用“发货 + 核销码”模拟履约，用 Outbox 表实现教学级事件驱动。

## 2.1 角色分析

系统共 6 个角色，其中 R5/R6 是系统参与者，不是人工操作员。R2 运营管理员与 R4 碳核证/风控在职责上分权：参数配置与账户调账不能由同一人完成。

| 编号 | 角色名 | 所属部门 | 简要描述 |
|---|---|---|---|
| R1 | 市民（出行用户） | 公众 / 城市居民 | 通过 Web 端上报步行、骑行、公交、地铁、共享单车行程；查询碳减排量与积分；浏览并兑换积分商城商品；查看订单与核销码；对异常记录申诉。 |
| R2 | 运营管理员 | 平台运营部 | 维护商品与 SKU、上下架、调库存；处理兑换订单（审核/发货/核销）；配置排放因子与积分参数；对异常账户冻结/调账；查看运营看板与对账报表。 |
| R3 | 商户（合作商家） | 外部合作机构 | 提供积分商城商品货源；接收新订单通知、确认发货、提交核销结果；查看本商户的兑换明细与结算单。 |
| R4 | 碳核证 / 风控专员 | 平台碳资产部 | 复核异常行程（距离越界、频次异常、瞬时速度不合理）；冻结可疑账户；处理事件死信与重放；确认碳减排量核算口径符合公示口径。 |
| R5 | 交通数据提供方（模拟） | 外部系统 | 以 HTTP 接口 / 定时任务推送或校验出行数据，是"出行数据采集"的触发者。本项目由模拟器实现，用于产生可复现的测试数据集。 |
| R6 | 定时任务（时间触发者） | 平台后台 | 触发每日积分清算、积分过期、报表生成、Outbox 事件重试与死信扫描；无人工操作界面，但作为系统参与者建模。 |

# 第二章 设计规格说明书

## 1 概述

设计目标是把需求转成可实现、可测试、可答辩的结构：核心账务强一致，通知/统计等副作用异步化，图与代码/数据库对得上。设计约束 C1–C8 如下：5 人 13 周、1–2 周迭代、单 MySQL 无 MQ、积分/库存强一致、事件不丢可重试、Windows 开发低运维、既定 Go/React 技术栈、可单测可演示。

**与实现的总体对齐声明**：本设计以仓库当前实现为基线；凡是目标态与当前实现不一致的，统一在 §4 表 4-1A 记录，不把目标写成现状。已核对的关键事实：目录只有 `apps/api/internal/{app,config,domain,eventbus,httpserver,repo}`，没有 `usecase`；repo 是手写 SQL，sqlc 未启用；Token 是自签 HMAC，不是标准 JWT；compose 已编入 mysql + api + web 三个 service；数据库 11 组迁移（000008 为数据迁移、000009 为 Outbox 租约、000010 为 `carbon_record.raw_points`、000011 为幂等键唯一索引改为 `(user_id, idempotency_key)`）、15 张表（含 000006 的 `point_batch_txn` 与 000007 的 `audit_log`）。

## 2.1 体系结构设计

### 2.1.1 架构决策与选型

**（1）候选方案与约束支持度**

**表 2-0　候选架构方案与约束支持度**

| 方案 | 组成 | 一致性 | 事件解耦 | 运维成本 | 对 13 周 / 5 人的适配 | 结论 |
|---|---|---|---|---|---|---|
| A. 经典三层同步单体 | Controller → Service → Repository，单 MySQL；积分发放、通知、统计全部同步调用 | 强（本地事务） | 弱：通知/统计与主链路耦合，失败会拖慢或回滚主链路 | 低 | 高：最容易在 2 周内跑通 | 作为基线，不选 |
| B. 分层单体 + 事务性 Outbox | 同一进程内分层；业务事务内写 `event_outbox`，消费者异步轮询 | 核心账务强一致；事件最终一致 | 强：业务与通知/统计解耦，事件可重试、可重放 | 中低：只需一张表 + 一个 Worker | 高：先跑通主链路，再补 Worker | **选用** |
| C. 微服务 + Kafka/RabbitMQ | 用户、行程、积分、商城、通知拆服务；MQ 做事件总线 | 最终一致；跨服务需 Saga / 补偿 | 最强 | 高：需要 MQ、服务发现、链路追踪、分布式事务 | 低：5 人 13 周无法稳定交付 | 不选 |

**表 2-0A　约束支持度对比**

| 约束 | A 同步三层 | B 单体 + Outbox | C 微服务 + MQ |
|---|---|---|---|
| C1 5 人 13 周 | 强 | 强 | 弱 |
| C2 1–2 周迭代 | 强 | 强 | 弱 |
| C3 单 MySQL、无 MQ | 强 | 强 | 弱（需新增中间件） |
| C4 积分/库存强一致 | 强 | 强（本地事务） | 中（Saga 补偿复杂） |
| C5 事件不丢、可重试 | 弱 | 强（Outbox） | 强（MQ 持久化） |
| C6 Windows 开发、低运维 | 强 | 强 | 弱 |
| C7 既定 Go/React 技术栈 | 强 | 强 | 中（多语言/多仓库） |
| C8 可单测、可演示 | 强 | 强（domain 纯函数） | 中（联调成本高） |

结论：A 能满足核心账务强一致，但事件解耦弱；C 的事件能力强，但 C1/C2/C3/C6 明显不满足；B 在“核心账务强一致 + 事件最终一致”之间取得平衡，是唯一同时满足 C1–C8 的方案。

**（2）架构决策与理由**

**表 2-1A　架构决策记录（ADR 摘要）**

| 编号 | 决策 | 备选与被否原因 | 状态 | 证据（文件/图） | 关闭条件 |
|---|---|---|---|---|---|
| ADR-01 | 采用**分层单体**，不拆微服务 | 微服务 + MQ：分布式事务、服务发现、链路追踪会吃掉 13 周工期 | 部分实施 | 图2-1；`httpserver/auth.go:34` 仍持 `*sql.DB`；行程事务已迁 `repo/trips.go`（`TripHandler` 只依赖 `app.TripStore`） | auth 改走 repo 后关闭 |

| ADR-07 | 部署目标为 compose 拉起 mysql + api + web + nginx | 本地双进程无法证明“一条命令”；上云超出范围 | 已实施配置 | `deploy/docker-compose.yml` 编入 mysql/api/web 三 service，11 组迁移全挂载；容器实跑受本机无 Docker 引擎限制，DEV-05 | 在有 Docker 的机器实跑并留记录 |

**为什么选“分层单体 + Outbox”**：

1. **一致性边界最小**：积分余额、库存、订单、流水必须在同一事务内完成。单库本地事务是最便宜、最容易讲清楚的强一致方案；拆微服务后同样的需求要引入 Saga、幂等补偿、对账，13 周内很难稳定。
2. **事件解耦但不引入 MQ**：选题建议用 EDA 解耦“出行后积分发放与清算”。Outbox 让行程上报只负责写事件，通知/统计/清算可以后置；消费者失败不回滚已发放积分。
3. **失败可恢复**：`event_outbox` 的 `attempts / available_at / dispatched_at / dead_letter_at / last_error` 支持退避重试与死信，这是同步调用没有的。
4. **可测试**：domain 是纯函数，HTTP 层注入端口，repo 才碰 SQL；45 个领域用例、75 个 HTTP 测试函数不需要 MySQL。
5. **成本匹配**：不需要 Kafka、Redis、服务发现；一张表 + 一个轮询 goroutine 即可，符合 5 人/13 周。

**代价与边界**：业务消费者尚未接入，Worker 当前不启动，事件保持待投递；Dispatch 先短事务认领五分钟租约再执行 handler。租约到期可能重复投递，消费端必须幂等；Outbox 表会膨胀，教学项目暂不做归档。

### 2.2.2 关键程序逻辑设计

**图 2-14　兑换下单与积分批次扣减活动图**

![图2-14 活动图：兑换下单与积分批次扣减](docs/uml/out/图2-14%20活动图：兑换下单与积分批次扣减.png)

关键点：

1. **幂等先于事务**：`findOrderByIdem` 在 `BEGIN` 之前查；命中直接返回原订单，不重复扣分。并发下同一幂等键由 `uk_order_idem` 兜底，冲突后回读原订单。
2. **锁顺序固定**：先 `point_account` 行锁，再 `product_sku` 行锁；所有下单路径同一顺序，避免死锁。
3. **锁后复核**：商品 `ONLINE`、`stock > 0`、`balance − frozen ≥ price`、`limit_per_user` 未超限，全部在拿到行锁后判断，禁止“先查后写”。
4. **同一事务**：`redeem_order` + `point_txn(REDEEM)` + `point_account.balance` + `product_sku.stock` + `point_batch` 扣减 + `event_outbox(OrderPaid)` 同一 `tx`，任一步失败整体回滚。
5. **批次 FIFO 与不足失败**：`ORDER BY expires_at ASC, id ASC FOR UPDATE`，逐批扣 `remaining`；扣到 0 置 `CONSUMED`，每笔消耗写 `point_batch_txn`（amount 为负）。若循环结束 `need > 0`，必须 `ROLLBACK` 并返回 `409 BATCH_INCONSISTENT`；禁止“只扣可用批次、余额仍减”。设计以本图为准；当前 `consumeBatches` 已实现 FIFO 扣减、明细写入与不足失败（`available < need` 返回 `app.ErrInsufficientPoints`，PR #40），但仍未过滤 `expires_at`，过期批次可能被扣，属 DEV-03。
6. **取消原路回滚**：只允许 `PENDING`；补 `REFUND` 流水，先按 `point_batch_txn` 把已消耗批次原路回填（`expires_at` 不变，amount 为正），未覆盖部分才新建退款批次；再退余额、回补库存、置 `CANCELLED`、写 `OrderCancelled` 事件；不修改原 `REDEEM` 流水。

**图 2-15　发放积分与批次写入活动图**

![图2-15 活动图：发放积分与批次写入](docs/uml/out/图2-15%20活动图：发放积分与批次写入.png)

发放路径必须与扣减对称：`point_txn(TRAVEL)` 落账后，同一事务写 `point_batch(granted_amount, remaining, expires_at)`，并让 `grant_txn_id` 指向该流水；日上限只影响 `granted_amount`，不改变批次与余额的一致性。当前 `repo/trips.go` 的 `CreateTrip` 已在同一事务调用 `GrantPointsWithBatch` 写 `point_batch`；剩余缺口是 `consumeBatches` 未过滤过期批次（批次不足已由 PR #40 改为失败回滚），属 DEV-03；本图按“现状 + 缺口”标注，不写成全部已实现。

### 3.1.1 类模型到关系表模型的转换规则

分析类图只表达业务概念，落到 MySQL 表时按以下规则转换；规则之外不临时加表、不加字段。

1. **实体类 → 表**：类名转 `snake_case` 复数/业务名（`PointAccount` → `point_account`）；主键统一 `id BIGINT UNSIGNED AUTO_INCREMENT`；审计列 `created_at`、`updated_at DATETIME(3)`。
2. **1:1 关联**：共享主键或“外键 + 唯一索引”。本系统 `User` 与 `PointAccount` 为 1:1，落为 `point_account.user_id` + `uk_point_account_user`；不另建中间表。
3. **1:N 关联**：多端持外键，单端不存集合。`User → TripRecord` 落为 `trip_record.user_id`；`PointAccount → PointTxn` 落为 `point_txn.account_id`；`Product → ProductSku` 落为 `product_sku.product_id`。
4. **M:N 关联**：必须落关联表，关联表可带业务属性。`RedeemOrder` 是 `User × ProductSku` 的关联实体，除两个外键外还承载 `points_spent`、`status`、`redeem_code`、`idempotency_key`；`PointBatchTxn` 是 `PointBatch × PointTxn` 的关联表，`amount` 为负表示消耗、为正表示回填。
5. **继承/多态**：本系统没有类继承，不引入单表继承或 `class_name` 判别列；若后续出现，优先“单表 + 判别列”，不为每个子类建表。
6. **组合/强依赖**：整体删除时部件必须同事务删除。`CarbonRecord` 依赖 `TripRecord`（1:1，`uk_carbon_trip`）；`PointBatchTxn` 依赖 `PointBatch` 与 `PointTxn`（联合唯一 `uk_pbt_batch_txn`）。数据库不建 `ON DELETE CASCADE`，由 repo 事务保证。
7. **枚举**：状态、类型、角色用 `ENUM` 落库，取值与领域常量、UML 状态图一一对应；会变的字典（出行方式、排放因子）单独建 `travel_mode` 表，不用 `ENUM` 写死。
8. **弱实体**：没有独立业务主键、依附强实体的表，用“强实体外键 + 局部唯一键”。`PointBatchTxn` 以 `(batch_id, txn_id)` 唯一；`CarbonRecord` 以 `trip_id` 唯一。
9. **主外键与索引命名**：主键 `id`；逻辑外键 `<实体>_id`（`user_id`、`sku_id`、`batch_id`）；唯一索引 `uk_<表>_<语义>`；普通索引 `idx_<表>_<语义>`。全部逻辑外键，不建物理 `FOREIGN KEY`，关联完整性由 repo 事务与业务校验保证。

**核心代码 2：批次 FIFO 扣减与不足失败**（逐字摘自 `apps/api/internal/repo/batches.go:40-96`）

```go
rows, err := tx.QueryContext(ctx,
    `SELECT id, remaining FROM point_batch
     WHERE account_id = ? AND status = 'ACTIVE' AND remaining > 0
     ORDER BY expires_at ASC, id ASC FOR UPDATE`, accountID)
if err != nil {
    return err
}
type batch struct{ id, remaining int64 }
batches := make([]batch, 0, 8)
for rows.Next() {
    var b batch
    if err := rows.Scan(&b.id, &b.remaining); err != nil {
        _ = rows.Close()
        return err
    }
    batches = append(batches, b)
}
if err := rows.Err(); err != nil {
    _ = rows.Close()
    return err
}
_ = rows.Close()
var available int64
for _, b := range batches {
    available += b.remaining
}
if available < need {
    return app.ErrInsufficientPoints
}

left := need
for _, b := range batches {
    if left <= 0 {
        break
    }
    take := b.remaining
    if take > left {
        take = left
    }
    left -= take
    remaining := b.remaining - take
    status := "ACTIVE"
    if remaining == 0 {
        status = "CONSUMED"
    }
    if _, err := tx.ExecContext(ctx,
        `UPDATE point_batch SET remaining = ?, status = ? WHERE id = ?`,
        remaining, status, b.id); err != nil {
        return err
    }
    if _, err := tx.ExecContext(ctx,
        `INSERT INTO point_batch_txn (batch_id, txn_id, amount) VALUES (?, ?, ?)`,
        b.id, txnID, -take); err != nil {
        return err
    }
}
return nil
```

> 代码与设计偏差：真实 SQL 只筛 `status='ACTIVE' AND remaining > 0`，没有 `expires_at > NOW()`，过期批次仍可能被优先扣减；批次不足已由 `available < need` 检查返回 `app.ErrInsufficientPoints`（PR #40），调用方回滚。剩余缺口是过期过滤，见 DEV-03。

# 附录 C　术语

| 术语 | 含义 |
|---|---|
| Outbox | 事务性发件箱：业务事务内写事件，消费者异步投递 |
| FIFO | 积分批次按最早过期优先扣减 |
| 幂等 | 同一请求重复提交不产生重复副作用 |
| 逻辑外键 | 只保留关联字段与索引，不建数据库物理外键 |
| 核销码 | 兑换订单的履约凭证，运营/商户完成时校验 |
