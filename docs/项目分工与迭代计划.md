## 2. 领域规则先定稿（P1 主责，全员评审，Sprint 1 第 1 周冻结）

这一节是全组的地基，写死之后前端、后端、测试才能并行。

### 2.1 碳减排量计算

```
baseline(t)  = distance(t) × EF[出行方式 t]        # 该方式若改为"燃油私家车"的基准排放
actual(t)    = distance(t) × EF_actual[t]          # 公交/地铁/骑行/步行的实际排放
carbon_saved(t) = max(0, baseline(t) - actual(t))  # 单位 gCO2e
```

参考排放因子（gCO2e/km，写进 `emission_factor` 种子数据，报告里注明来源口径）：

| 出行方式 | EF 基准（燃油小汽车） | EF_actual |
|---|---|---|
| 步行 walk | 192 | 0 |
| 骑行 bike | 192 | 0 |
| 地铁 subway | 192 | 41 |
| 公交 bus | 192 | 68 |
| 共享单车 shared_bike | 192 | 0 |

### 2.2 积分生成

```
points = floor(carbon_saved_g / CARBON_PER_POINT)   # CARBON_PER_POINT 默认 100 gCO2e = 1 积分
```
- 参数 `CARBON_PER_POINT`、各 EF 值全部放配置表，**不得硬编码**。
- 单次行程距离上下限（如 0.1–100 km）与单日积分上限（如 500）为业务约束，需在报告"业务规则"里建模。

### 2.3 不变量（写进测试用例的断言）

1. **账本等价**：`point_account.balance == Σ(point_txn.amount)`，任何时刻成立（有对账接口验证）。
2. **幂等**：同一 `user_id + trip_hash` 重复上报只产生 1 条出行记录、1 笔积分流水；`Idempotency-Key` 重复的兑换请求只扣一次。
3. **不超兑**：`balance - frozen >= 0`，扣减走 `SELECT ... FOR UPDATE` 或带条件的 UPDATE，禁止先查后写。
4. **状态机**：订单 `PENDING → PAID → SHIPPED → COMPLETED`，可 `CANCELLED`；非法跃迁必须被拒绝且有测试覆盖。
5. **可追溯**：任何一笔积分变动都能反查到来源（行程 / 兑换 / 人工调整 / 过期）。

### 2.4 核心数据库表（P2/P3 共同实现，P1 出字段级清单）

`user`、`travel_mode`、`emission_factor`、`trip_record`、`carbon_record`、`point_account`、`point_txn`、`merchant`、`product`、`product_sku`、`redeem_order`、`event_outbox`、`audit_log`、`admin_user`、`sys_config`（≈15 张）。

约定：
- 金额与积分统一用 `BIGINT`（积分为整数，避免浮点误差）；碳排放保留 `DECIMAL(12,3)`。
- 所有表 `id BIGINT UNSIGNED AUTO_INCREMENT`、`created_at/updated_at DATETIME(3)`、软删 `deleted_at`。
- 积分流水表 `point_txn` **只插入不更新**（append-only），余额表仅作缓存快照。

### 2.5 事件驱动（EDA）落地方式

选题明确建议 EDA，教学场景不要上 Kafka/RabbitMQ，用**事务性 Outbox 表**即可：

```
上报行程（单事务）：
  INSERT trip_record + INSERT carbon_record + INSERT point_txn + 更新 point_account
  + INSERT event_outbox(type=TripVerified, payload=...)
后台 Worker（轮询 outbox）：
  TripVerified → 更新碳减排统计 / 触发成就徽章 / 写排行榜
  OrderPaid    → 扣减库存 / 通知商户 / 生成核销码
```
这一点在报告"?2.1.1 架构决策与选型"里对比 "经典分层同步调用" vs "EDA+Outbox"，给出**为什么选 EDA**的理由。

## 5. 协作规范（Git 与接口契约）

### 5.1 仓库结构（monorepo）

```
green-travel-points/
├─ apps/
│  ├─ api/                    # Go 后端（P2/P3）
│  │  ├─ cmd/server/          # 入口
│  │  ├─ internal/domain/     # 实体与业务规则（碳核算、积分）
│  │  ├─ internal/usecase/    # 应用服务（用例实现，与报告序列图对应）
│  │  ├─ internal/repo/       # sqlc 生成 + 手写查询
│  │  ├─ internal/handler/    # HTTP 层
│  │  └─ internal/eventbus/   # Outbox + Worker
│  ├─ web/                    # 用户端（P4）：Vite + React + TypeScript 7
│  └─ admin/                  # 运营后台（P5）
├─ packages/api-types/        # OpenAPI 生成的前端类型（P4 维护，P2 保证 spec 同步）
├─ db/migrations/             # golang-migrate 迁移（P2/P3）
├─ docs/                      # 报告、UML 源文件、会议记录
│  ├─ uml/                    # PlantUML 源文件（P1）→ 导出 PNG 进报告
│  └─ 项目分工与迭代计划.md    # 本文件
├─ deploy/                    # docker-compose.yml、Dockerfile、nginx.conf
└─ .github/                   # PR 模板、Actions（lint + test + build）
```

### 5.2 分支与提交

- 主干 `main` 受保护，只接受 PR；分支命名 `feat/M2-trip-report`、`fix/M7-oversell`。
- **Conventional Commits**：`feat(api): 实现行程上报接口 (#12)`；一条提交只做一件事，避免"一周一大坨"（互评表要按提交记录打分）。
- PR 需 1 人 Review + CI 绿才能合并；PR 描述里写"对应报告章节/图号"，方便后期统稿。
- 每个 Sprint 末打 Tag，并在 Release 里附增量说明（报告 1.2 可直接引用）。

### 5.3 接口契约先行

1. P1 + P2 在 Sprint 2 第 1 周产出 `docs/api/openapi.yaml`（≥20 个端点）。
2. P4 用 `openapi-typescript` 生成前端类型：**前端不手写 DTO**，改契约 → 重新生成 → `tsc` 报错点即改动点。
3. 后端用统一响应包装与错误码表（`{code, message, data}`），P5 的接口测试直接按错误码断言。

### 5.4 时间与沟通

- 每周 1 次 30 分钟站会（周三），记录写进 `docs/meetings/`（也是报告里"协作过程"的证据）。
- 任务粒度：单个任务 ≤ 2 天；看板列 `Backlog / Ready / In Progress / Review / Done`。
- 阻塞超过 1 天必须在群里同步，由 P1 决策是否调整范围。
