### P0（1 项）

#### P0-2（P0）积分批次扣减/回填不闭环：过期批次可花、批次不足静默成功、退款复活过期批次

- **配合**：P2、P1、P5
- **位置**：apps/api/internal/repo/batches.go:34-88、92-155；apps/api/internal/repo/orders.go:171、278；apps/api/internal/repo/admin.go:469。
- **问题说明**：consumeBatches 未过滤 expires_at，过期但未清算的批次仍可扣；left>0 被忽略，调用方仍扣余额/库存；restoreBatches 直接置 ACTIVE，复活过期/已冲正批次；人工调减同样吞掉批次不足。
- **修改建议**：consumeBatches 增加 expires_at > NOW(3)，left>0 返回 app.ErrInsufficientPoints；restoreBatches 带 expires_at/status 校验，过期批次跳过，由调用方为差额新建批次，并校验 remaining+qty<=granted_amount；补 seed 批次，避免演示用户 1001 严格校验后无法下单；补过期/不足/回填/调减测试。
- **验收标准**：过期批次不可扣；批次不足整单回滚并返回 INSUFFICIENT_POINTS；过期后取消不会复活旧批次，差额生成新批次；seed 用户 1001 有可用批次；4 类集成测试通过。

### P1（1 项）

#### P1-11（P1）ReconcilePoints 只对“余额=流水和”，批次/冻结完全没查，容易给出假 OK

- **配合**：P2、P5、P1
- **待业务确认**：frozen 的业务语义（冻结积分是否仍在批次内）需 P1/设计文档确认；决定对账等式是 balance=batch_sum 还是 balance-frozen=batch_sum。
- **位置**：apps/api/internal/repo/admin.go:360-386。
- **问题说明**：当前 SQL 只比较 point_account.balance 与 SUM(point_txn.amount)，这个恒等式正常写路径下几乎必然成立，发现不了批次缺口、过期未清算、frozen 异常；报告却把它当“全量对账”证据。
- **修改建议**：增加 batch_sum（ACTIVE 且未过期批次的 remaining 和）与 frozen 合法性；返回 BatchSum/Frozen 字段；补“人为制造批次缺口”的集成测试；报告中的对账证据改用新结果。
- **验收标准**：对账能报出余额与批次和不一致、frozen<0 或 frozen>balance；正常账本返回 OK；集成测试覆盖批次缺口；报告引用真实对账输出。

### P2（7 项）

#### P2-12（P2）RowsAffected()==0 被当成“不存在”，同值更新会误报 404

- **配合**：P5
- **位置**：apps/api/internal/repo/admin.go:218-229、238-249。
- **问题说明**：MySQL 默认 RowsAffected 返回实际改变行数，不是匹配行数；商品/库存改成原值时影响 0 行，代码返回 ErrNotFound。
- **修改建议**：RowsAffected==0 时 SELECT 1 判断存在性，无行才 404；或 DSN 加 clientFoundRows=true，但要全仓确认语义；补同值更新用例。
- **验收标准**：商品名/库存改成原值返回 200；不存在的 id 返回 404；补 product 与 SKU stock 两组 HTTP/集成测试。

#### P2-13（P2）商品创建缺应用层校验，负限购/超长字段会变成 500

- **配合**：P5、P1
- **位置**：apps/api/internal/httpserver/admin.go:47-74；apps/api/internal/repo/admin.go:120-171。
- **问题说明**：handler 未校验 limitPerUser<0、名称>128、描述>500、分类>32、封面>255、SKU 名>64、同请求 SKU 重名；DB CHECK/严格模式报错后变成 500。
- **修改建议**：在 app 增加纯函数 AdminProductInput.Validate()，用 utf8.RuneCountInString 校验长度、limit>=0、SKU 非空/价格>0/库存>=0/重名；handler 与 repo 都调用；返回 400 + 具体字段。
- **验收标准**：负限购、129 字名称、501 字描述、重复 SKU 均返回 400 且指出字段；不出现 DB 500；补表驱动/HTTP 用例。

#### P2-14（P2）人工调账可能 int64 溢出，调减还忽略批次不足

- **配合**：P2、P5
- **位置**：apps/api/internal/repo/admin.go:429、469。
- **问题说明**：after := balance + in.Amount 无溢出检查，in.Amount 无绝对值上限；调减分支调用 consumeBatches 但忽略批次不足（修 P0-2 后会返回错误，需同步处理）。
- **修改建议**：限制单次调账绝对值（如 1,000,000）且非 0；加法前检查 balance > math.MaxInt64-in.Amount；调减分支处理 consumeBatches 错误并回滚。
- **验收标准**：amount=0/±1,000,001 返回 400；溢出输入返回 400；批次不足返回 409 并回滚；补边界测试。

#### P2-15（P2）审计链有缺口：过期清算无审计，配置/出行方式理由写死，非法操作人变成“不过滤”

- **配合**：P5、P1
- **位置**：apps/api/internal/httpserver/admin.go:174-181、197-240、263-279；apps/api/internal/repo/admin.go:556-565、673。
- **问题说明**：expirePoints 不接收操作人/理由，不写 audit_log；UpdateConfig/UpdateTravelMode 理由硬编码；auditLogs 的 operatorId 解析失败变 0，repo 把 0 当“不过滤”，返回全量日志。
- **修改建议**：ExpirePoints(ctx, operatorID, reason) 写 audit_log（action 增加 POINTS_EXPIRE）；配置/出行方式请求增加 reason 必填并透传；operatorId 非法直接 400；开发期改迁移并重建库。
- **验收标准**：过期清算有操作人/理由/前后值/数量；配置/出行方式无 reason 返回 400；operatorId=abc 返回 400；补审计查询/写入测试。

#### P2-17（P2）订单号只有 4 位随机数且忽略 rand.Read 错误，高并发下会碰撞

- **配合**：P2、P5
- **位置**：apps/api/internal/repo/orders.go:402-418。
- **问题说明**：newOrderNo 使用 RO+秒级时间+uint16%10000，同一秒只有 1 万个可能，唯一键冲突直接 500；rand.Read 错误被忽略；newRedeemCode 同样忽略。
- **修改建议**：订单号用 8 字节随机（hex 16 位）或 ULID；rand.Read 错误返回；插入冲突重试 2–3 次；核销码保留 32 字符表并处理错误。
- **验收标准**：10k 次生成无重复（测试）；rand 失败时返回错误而不是零值；唯一键冲突有重试；补生成器测试。

#### P2-18（P2）pointsExpireDays 在调用方事务内另开 s.db 查询，且错误静默回退 365

- **配合**：P2
- **位置**：apps/api/internal/repo/orders.go:381-393；调用点 283、464。
- **问题说明**：CancelOrder/AdjustPoints 已持有账户行锁，pointsExpireDays 又用 s.db 开第二条连接查 sys_config；快照不一致、连接池受限时可能互等；任何错误静默返回 365。
- **修改建议**：BeginTx 之前读取 points_expire_days，把值传入事务；函数返回 (int64,error)，配置缺失/非法直接失败；不要在事务内查配置。
- **验收标准**：事务内无 s.db 查询；配置缺失返回明确错误；过期日使用传入值；补配置缺失/正常值测试。

#### P2-21（P2）状态机允许 PAID/SHIPPED→CANCELLED，但 API 没有入口，两个状态实际不可达

- **配合**：P1、P4、P5
- **待业务确认**：PAID/SHIPPED 是否允许取消，需 P1/产品确认；选 A 加管理员取消，选 B 删不可达边。
- **位置**：apps/api/internal/domain/order.go:23-28；apps/api/internal/repo/admin.go:301-305；apps/api/internal/repo/orders.go:251。
- **问题说明**：domain 允许 PAID/SHIPPED→CANCELLED，但用户 CancelOrder 只允许 PENDING，管理员 TransitionOrder 只接受 PAID/SHIPPED/COMPLETED 目标，没有 CANCELLED；两个流转只存在于文档/domain。
- **修改建议**：二选一，需产品确认：A 增加管理员取消 PAID/SHIPPED 的接口，复用退款/回补库存/审计；B 从 domain 与 README 删除这两条流转，只保留 PENDING→CANCELLED。
- **验收标准**：若选 A，PAID/SHIPPED 取消可退款/回补库存/写审计并有测试；若选 B，domain 映射/README/报告三者一致且无不可达边；API 测试与状态机测试一致。
